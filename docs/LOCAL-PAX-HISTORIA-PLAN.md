# 로컬 Pax Historia 제작 계획서

v1.2 (2026-07-28) · 베이스: Open-Historia 포크 · 용도: 개인용 로컬 전용 · 변경: v1.1 프리셋·규칙 이식 추가 → v1.2 OpenHistoricalMap 역사 판도 임포트 편입, 업데이트 스크립트 리스크 추가, 진행 현황 반영

---

## 1. 목표와 비목표

**목표.** Open-Historia를 포크해서, Ollama 로컬 모델을 메인 두뇌로 쓰는 개인용 Pax Historia를 만든다. 원본(paxhistoria.co)의 게임 느낌 — 이벤트 서술 스타일, 상태 표현 방식, 화면의 분위기 — 을 분석해서 로컬 버전에 이식하되, 코드 구조는 Open-Historia를 유지해 업스트림 업데이트를 계속 받을 수 있게 한다.

**비목표 (인터뷰에서 명시적으로 제외한 것들).**

- ChatGPT 구독 OAuth 연동 — API 키 방식으로 충분하다고 결정. 비공식 우회의 ToS 리스크를 지지 않는다.
- 배포/패키징 — 나 혼자 쓰는 물건. 인스톨러, 코드사이닝, 다른 사람의 토큰 보안은 설계에서 뺀다.
- 전면 UI 리스킨 — 분위기·톤만 참조. 구조를 갈아엎으면 업스트림 머지가 죽는다.
- 코드베이스 신규 제작 — Open-Historia가 이미 게임 루프, 맵, 시나리오 허브까지 갖추고 있다.

## 2. 인터뷰로 확정된 사항

| 항목 | 결정 |
|---|---|
| 베이스 | Open-Historia 포크·개조 |
| AI 메인 | Ollama (로컬), 12–16GB VRAM → 14B급 모델 |
| AI 옵션 | 클라우드 프로바이더는 API 키 입력 (기존 방식 유지) |
| 추가할 AI 기능 | ① 커스텀 프로바이더 다중 저장 ② 역할별 모델 분리(heavy/light 2단계 + 기능별 오버라이드) ③ 더 편한 선택 UI |
| 원본 참조 | paxhistoria.co (계정 보유) — UI 톤 + 게임 상태·프롬프트 구조, 디스코드 패치노트, 위키(일반 정보) |
| UI 방침 | 분위기·톤만 참조, 구조 유지 |
| 1단계 | 원본 분석부터 |

## 3. 포크 전략

```
upstream (Open-Historia/open-historia) ──> main   (추적만, 손대지 않음)
                                            └──> local-pax  (모든 개조는 여기)
```

- `main`은 업스트림 추적 전용으로 깨끗하게 유지하고, 개조는 전부 `local-pax` 브랜치에서 한다. 업스트림이 갱신되면 `main`을 당겨온 뒤 `local-pax`에 리베이스/머지한다.
- 개조 파일을 최소화한다: 새 기능은 가능하면 새 파일로 추가하고, 기존 파일 수정은 AI 설정 계층(아래 5절)에 집중시킨다. 충돌 표면적이 작을수록 업스트림을 오래 따라갈 수 있다.

## 4. Phase 1 — 원본 분석 (최우선)

목표는 "원본 대비 뭐가 부족한지"를 문서로 만드는 것. 개조는 이 문서가 나온 뒤에 시작한다.

### 4.1 게임 상태·프롬프트 구조 캡처

Pax-Automata를 그대로 재활용한다. 이 레포는 이미 원본의 `/api/simple-chat` 요청을 인터셉트해 전체 게임 상태(맵, 부대, 이벤트, 외교)를 뽑아내는 Spy 모듈을 갖추고 있다.

1. `npm run capture-auth`로 원본 계정 로그인 세션 저장 → `npm run interactor`로 게임 1판을 열어 여러 턴에 걸쳐 상태를 수집한다.
2. 수집한 `current_state.json`들에서 원본의 상태 포맷을 정리한다: 섹션 구성, 국가 상태 서술 방식, 이벤트 텍스트 스타일, 외교 표현.
3. 어드바이저 시스템 프롬프트(요청 페이로드에 포함됨)에서 원본이 AI에게 지시하는 톤·규칙을 추출한다.
4. 캡처는 이식 대상 프리셋마다 반복한다 — 프리셋별 시스템 프롬프트·시뮬레이션 규칙이 Phase 3 프리셋 이식 파이프라인의 원료가 된다. 첫 세션에서 이식하고 싶은 프리셋 목록부터 정할 것.
5. 산출물: `docs/analysis/state-format.md` — 원본 상태 포맷 명세 + Open-Historia의 `promptContext.js` 출력과의 비교표, 그리고 프리셋별 캡처 원본(`docs/analysis/presets/<프리셋명>/`).

### 4.2 UI 톤 캡처

Claude in Chrome(현재 열려 있는 크롬)으로 원본 사이트에 접속해 주요 화면을 캡처한다: 시작 화면, 국가 선택, 인게임 HUD, 이벤트 팝업, 어드바이저/외교 채팅. 캡처에서 디자인 토큰만 추출한다 — 색 팔레트, 폰트 계열, 간격 감각, 팝업/패널 스타일. 산출물: `docs/analysis/design-notes.md` (스크린샷 + 토큰 목록). 픽셀 단위 모사가 아니라 "왜 원본이 더 게임답게 느껴지는가"를 언어화하는 게 목적이다.

### 4.3 기능 패리티 백로그

디스코드 Pax Historia 채널의 패치노트를 훑어 원본의 기능 목록을 만들고, Open-Historia 현황과 대조한다. 산출물: `docs/analysis/parity-backlog.md` — 각 항목에 [있음 / 부분 있음 / 없음 / 안 만들 것] 판정. 이 백로그가 Phase 3의 작업 목록이 된다. 위키는 게임 규칙·용어 확인용 보조 자료로만 쓴다.

### 4.4 현재 상태 베이스라인

포크를 빌드해서 Ollama(14B)로 실제 한 판을 돌려본다. 기록할 것: 이벤트 생성이 JSON 스키마(`gameplaySchemas.js`, 38KB)를 몇 %나 통과하는지, 턴당 소요 시간, 컨텍스트 길이 초과 여부, 체감 품질. 이 숫자가 없으면 Phase 2의 개선을 측정할 수 없다.

> **주의 — Ollama 컨텍스트 함정:** Ollama 기본 컨텍스트는 짧게 잡혀 있어(모델별 2k~8k), Open-Historia의 게임 상태 프롬프트가 조용히 잘려나갈 수 있다. 베이스라인 측정 전에 `num_ctx`를 16k 이상으로 올린 모델을 만들어 두고 시작할 것. "로컬 모델이 멍청한 게" 아니라 "프롬프트가 잘린" 경우가 많다.

## 5. Phase 2 — AI 백엔드 개조

Open-Historia에는 이미 프로바이더 5종(Gemini/OpenAI/Anthropic/OpenAI-호환/Anthropic-호환), 모델 목록 조회, 커스텀 파라미터가 있다. 만드는 것은 그 위의 **프로필 계층**이다.

### 5.1 프로바이더 프로필 시스템

현재 구조는 프로바이더당 슬롯 1개(`providerConfig.js`의 localStorage 키 고정)다. 이를 이름 붙은 프로필 배열로 확장한다.

- 프로필 = `{ id, 이름, 프로바이더 종류, endpoint, apiKey, model, customParams }`. 예: "Ollama-qwen3", "Ollama-경량", "OpenRouter-무료", "OpenAI-비상용".
- 저장은 localStorage에 JSON 배열로, 기존 키는 첫 프로필로 자동 마이그레이션(기존 `legacyKeys` 패턴을 따라가면 된다).
- 프로필 내보내기/가져오기(JSON 파일) — 재설치·브라우저 프로필 이동 대비.
- 수정 지점: `src/Game/AI/providerConfig.js`(저장 계층), `src/Game/GameUI/settings.jsx`(설정 UI), `src/Game/AI/main.jsx`(호출부가 프로필을 받도록).

### 5.2 역할별 모델 매핑

AI 호출을 역할로 태깅하고, 역할→프로필 매핑 테이블을 둔다.

- 역할 축: `event`(이벤트/턴 진행 생성 — 무겁고 스키마 강제), `advisor`(고문·인텔 브리핑), `chat`(외교 채팅), `translate`(번역).
- 결정된 UX: **2단계 프리셋이 기본, 기능별 오버라이드가 고급 설정.** 기본 화면에서는 Heavy 프로필/Light 프로필 두 개만 고르면 event→Heavy, 나머지→Light로 배정된다. 고급 패널을 열면 역할별로 개별 프로필을 지정할 수 있다.
- 수정 지점: `main.jsx`의 `callAI` 진입점에 role 파라미터를 추가하고, 호출하는 쪽(`gameplay.js`, `advisor.jsx`, `chat.jsx`, `translator.js`)에서 역할을 넘긴다. 호출부 수정은 파라미터 추가 수준으로 얕게 유지한다.

### 5.3 선택 UI 개선

- Ollama 자동 감지: `http://localhost:11434/api/tags`를 조회해 설치된 모델을 드롭다운으로 제시 (기존 `providerSupportsModelDiscovery`가 openai-호환에서 이미 절반은 해준다 — 연결 안내와 원클릭 프로필 생성을 얹는 것).
- 프로필별 "연결 테스트" 버튼: 1토큰짜리 호출로 endpoint/키/모델 유효성 즉시 확인.
- 상단 바 어딘가에 현재 Heavy/Light 프로필 표시 + 원클릭 프리셋 전환("전부 로컬" / "하이브리드" / "전부 클라우드").

### 5.4 로컬 모델 신뢰성 (14B 전제)

이벤트 생성이 스키마를 깨면 게임이 멈추므로, 이 항목이 Phase 2의 실질적 핵심이다.

- Ollama의 structured output(`format`에 JSON 스키마 전달)을 이벤트 생성 경로에 적용 — 문법 수준에서 스키마를 강제한다.
- 실패 시 계단식 대응: ① 같은 모델 재시도(오류 메시지 포함) → ② 스키마 리페어 시도 → ③ 지정된 폴백 프로필(예: 클라우드 API)로 1회 위임. 각 단계는 설정에서 켜고 끌 수 있게.
- 베이스라인(4.4) 대비 스키마 통과율을 다시 측정해 효과를 확인한다.

**권장 모델 구성 (12–16GB VRAM):**

| 역할 | 1순위 | 비고 |
|---|---|---|
| Heavy (event) | qwen3:14b | 구조화 출력·지시 준수가 동급에서 강한 편 |
| Heavy 대안 | gpt-oss:20b | MXFP4로 16GB에 들어감. 베이스라인에서 둘을 비교 측정 후 결정 |
| Light (advisor/chat/translate) | qwen3:8b 또는 llama3.1:8b | 체감 반응속도 우선 |
| 폴백 (선택) | 클라우드 API 키 프로필 1개 | 스키마 연속 실패 시에만 호출 |

## 6. Phase 3 — 게임 필 이식

Phase 1 산출물이 작업 목록이 된다. 순서는 백로그에서 그때 정하되, 세 갈래로 나뉜다.

- **프롬프트 이식:** `state-format.md`의 분석을 바탕으로 Open-Historia의 프롬프트(`promptContext.js`, `defaultPrompts.json`, `gameplayPrompts.js`)에 원본의 상태 서술 방식·이벤트 톤을 반영한다. 프롬프트는 코드가 아니라서 업스트림 충돌 부담이 작고, 게임 느낌에 미치는 영향은 가장 크다.
- **프리셋·시뮬레이션 규칙 이식 (외부 이식 파이프라인):** 원본 Pax Historia의 프리셋(시나리오)들에서 프리셋별 시스템 프롬프트와 시뮬레이션 규칙을 가져올 수 있는 반복 가능한 이식 경로를 만든다. 4.1의 캡처 세션을 이식 대상 프리셋마다 반복해(예: 모던, WWII 등) 프리셋별 상태 포맷·규칙 서술·이벤트 스타일·시대 제약(병종, 기술 수준 등)을 수집하고, 이를 Open-Historia의 시나리오 체계 — 프리셋 spec(`scripts/presets/*.spec.mjs`)과 시나리오 에디터의 프롬프트/규칙 필드 — 로 매핑하는 변환 절차를 정한다. 처음엔 문서화된 수작업 절차로 시작하고, 프리셋 2~3개를 이식해 패턴이 잡히면 반자동 변환 스크립트(캡처 JSON → 시나리오 번들)로 승격한다. 목표: "원본 프리셋 N개를 로컬 시나리오로 재현"이 한 번의 절차로 가능해지는 것.
- **기능 이식:** `parity-backlog.md`에서 [없음] 판정 중 원하는 것을 골라 구현한다. 계획 시점에 목록을 확정하지 않는다 — 분석 전에 정하는 목록은 틀리기 마련이다.
- **역사 판도 임포트 (OpenHistoricalMap 통합):** 앞으로 추가될 역사 시나리오의 국경·행정구역을 실제 역사 데이터로 만들 수 있게, [openhistoricalmap.org](https://www.openhistoricalmap.org)를 프로젝트에 연결한다. 흐름: 대상 날짜 지정 → OHM Overpass API(개체별 `start_date`/`end_date` 필터)로 해당 시점의 `boundary=administrative` 폴리곤 추출 → turf로 단순화 → Open-Historia의 지역+소유(regions/owners) 구조로 매핑 → 맵 에디터의 기존 geojson 임포트 경로 또는 프리셋 spec(`scripts/presets/`)으로 출력. 1차 프로토타입은 특정 날짜·특정 대륙(예: 1826 유럽)의 국경선 스크립트로 시작하고, 잘 되면 에디터에 "역사 날짜로 국경 불러오기" UI로 승격. 유의: OHM은 커뮤니티 지도라 시대·지역별 커버리지 편차가 크므로(빈 곳은 에디터 수동 보정과 결합), 그리고 ODbL 라이선스 표기가 필요하다(개인용은 부담 없음).

## 7. Phase 4 — UI 톤 정리

`design-notes.md`의 디자인 토큰을 `src/styles.css`와 컴포넌트 인라인 스타일의 색·폰트 변수 수준에서 반영한다. 컴포넌트 구조(JSX 트리)는 건드리지 않는다. 이 단계는 가장 뒤로 미뤄도 게임성에 지장이 없고, 업스트림 충돌 리스크 대비 효용이 가장 낮으므로 마지막이다.

## 8. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 14B가 이벤트 스키마를 계속 깨뜨림 | 5.4의 structured output + 계단식 폴백. 그래도 안 되면 event 역할만 클라우드로 — 하이브리드가 차선책임을 처음부터 인정 |
| Ollama 컨텍스트 잘림 | `num_ctx` 16k+ 커스텀 모델로 시작 (4.4 주의사항) |
| 업스트림 머지 충돌 | 개조를 프로필 계층 + 프롬프트 + CSS 토큰에 집중, `main` 추적 브랜치 유지 |
| 원본 인터셉트 깨짐 (사이트 개편) | Pax-Automata의 알려진 약점(README 명시). 분석은 초반에 몰아서 끝내고, 이후엔 의존하지 않는 구조로 |
| 원본 콘텐츠 이용 범위 | 개인 분석·참조용으로 한정. 추출한 프롬프트·디자인을 재배포하지 않는다 (포크 자체는 MIT 준수) |
| 스코프 팽창 | 패리티 백로그에 [안 만들 것] 열을 두고 명시적으로 버린다 |
| **Update 스크립트가 로컬 패치를 덮어씀** | 현재 개조는 ZIP 설치본의 src에 직접 적용돼 있어 `Update Open Historia` 실행 시 전부 사라진다. 실행 전 반드시 패치 파일(`local-pax-all-features.patch`) 보관 확인, 근본 해결은 포크(git) 이전 |
| OHM 커버리지 공백 | 시대·지역별로 데이터가 빈 곳은 맵 에디터 수동 보정과 병행, 임포트 도구는 "빈 지역 목록"을 출력해 보정 대상을 알려주게 설계 |

## 9. 바로 시작하는 체크리스트

1. Open-Historia 포크 → `local-pax` 브랜치 생성
2. `num_ctx` 16k의 qwen3:14b 변형 모델 생성 (`ollama create`)
3. 빌드 후 Ollama 연결(openai-호환, `http://localhost:11434/v1`)로 한 판 — 베이스라인 기록 (4.4)
4. Pax-Automata `capture-auth` → 이식할 프리셋 목록 확정 후 프리셋별 원본 상태 캡처 세션 (4.1)
5. 크롬으로 원본 화면 캡처 → 디자인 노트 (4.2)
6. 디스코드 패치노트 정리 → 패리티 백로그 (4.3)
7. 분석 문서 3종 리뷰 후 Phase 2 착수
